Agent 的终点不是「看见异常」，是「关单」

Lau · 2026-11-11 · PulseOps 设计复盘

离散制造车间里，一条产线 4 台设备，值班的是班组长和 2 个维修工。没人盯得住 24 小时的曲线——异常通常在「已经停机之后」才被发现，工单靠口头传，处置结果留在师傅脑子里。

市面上很多「设备大屏」的终点是「看见异常」：曲线、告警、标红，很热闹。但看见之后呢？谁去处理、处理结果记在哪、下次同类故障能不能直接查到——这些才是真正决定价值的部分。

PulseOps 的定位就是把这后半截做成闭环：巡检发现异常 → LLM 诊断根因 → 幂等建单 → 飞书推卡片 → 群里点按钮处置 → 关单自动沉淀经验。

把不确定性关进一个格子

Agent 项目最常见的坑，是把「不稳定的模型」铺满整条链路，结果一个环节抖动，整个流程瘫痪。

PulseOps 的做法是给每个环节指定角色：

  • 巡检——确定性代码（Cron），定时取最新指标比阈值，越限就进诊断；已有未闭环工单就跳过。
  • 诊断——LLM，可降级。模型挂了不影响流程推进，只影响诊断质量。
  • 工单——确定性代码，建单、发飞书卡片、校验状态流转、关单时写回知识库。

一句话：确定性代码兜底，LLM 只做它擅长的推理。这不是排斥模型，而是给不可靠的部分划定边界。

幂等是硬约束，不是优化项

巡检每几分钟跑一次，同一台设备、同一个异常，重跑不能凭空多出十张单。所以在「判异 → 建单」之间必须有一层幂等：已有未闭环工单时跳过，而不是再建一张。

这种约束在 demo 里看不出来，只有把系统放在「24 小时无人值守」的假设下，才会意识到它必须是对的，而不是「大部分时候对」。

闭环的证据

127 条回归用例 + GitHub Actions CI 卡在 PR 上，改动先过测试再说。飞书卡片点按钮后就地重绘成下一状态，处置结果在 3 秒预算内回写；关单时把这次处置沉淀成「故障码—症状—根因—处置」的知识条目，并带来源工单号溯源。

于是「这张单被谁、在什么时候、用什么办法关掉」——每一条都留痕，可审计。
