飞书卡片 3 秒预算——把一个工单闭环塞进一张卡，还带三级降级

Lau · 2026-11-12 · PulseOps 渠道复盘

PulseOps 的工单处置不在浏览器里，而在飞书群。对班组长和维修工来说，报警卡片就是一张随身的工单档案——他们不会去开网页，只想在群里把事办了。

一、一张卡 = 一张单的完整档案

卡片按工单生命周期组织：头部（设备 + 严重度着色，紧急红 / 一般橙）、指标区（超限项与实测值）、诊断区（根因 / 处置方案 / 置信度）、操作区（接单 → 已处理 → 确认闭环）、收尾（闭环后追加「📚 经验已沉淀：KN-xxxx」）。

关键是交互模型：点按钮后卡片就地重绘成下一个状态，不新发卡。群里的讨论上下文不被打散，一张单的状态演进始终停在同一个位置。

二、3 秒预算从哪来

飞书卡片回调有超时约束，超时会触发重试或失效。所以从收到按钮点击，到完成状态校验、落库、回写，必须在 3 秒预算内完成（回归测试里按 2.2 秒卡）。这个约束倒逼了两件事：状态机流转必须轻，LLM 不进入实时链路——点击翻译、409 翻译、卡片重建全部是确定性代码。

三、三级流式降级链

Agent 的回复卡片按能力逐级下降，任一级不可用就退下一级，用户侧最多少个动画：

  • Level 0——cardkit.v1.card.create(streaming_mode) + 增量内容，原生打字机；
  • Level 1——cardkit.v1.card.update 整卡 JSON 刷新；
  • Level 2——im.message.create + message.patch，整卡刷新，最差但一定能用。

降级是逐条回复现判的，没有持久化的能力缓存：权限一开通，下一条回复自动回到 Level 0。三件套（App ID / Secret / Chat ID）缺任一项，就退回 Webhook 纯文本——那条路上没有按钮，但信息不会丢。

四、诚实的边界

卡片回调依赖长连接：飞书侧断线重连期间点按钮会失败，靠重试与「状态已变化」提示兜住，但没有本地队列补偿。这条我写在 README 的「边界与取舍」里——渠道的可靠性边界，不该藏起来。

五、复盘

把交互做进群聊，本质是把系统的可靠性假设搬到第三方渠道上。3 秒预算是硬约束，就地重绘是体验，三级降级是生存线——三者缺一个，卡片就会从「好用的工单入口」退化成「一条只会响的提醒」。
