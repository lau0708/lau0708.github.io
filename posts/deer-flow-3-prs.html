怎么给 83k star 的开源项目提 3 个 PR：测试不对称就是 bug 定位器

Lau · 2026-09 · 开源贡献复盘

给 bytedance/deer-flow（一个 LangGraph Agent 框架）提的 3 个 PR 全部被合并了：

  • #5663 fix(runtime)：让原子线程操作共享同一个变更位置
  • #5703 fix(skills)：用户级安装的内容扫描改从自身配置解析
  • #5998 fix(channels)：为飞书 / 钉钉入站附件补上沙箱读权限位

三个 PR 的共同点是：都是自己挖的 bug，没抢 issue，也没先问维护者。diff 都很小（含测试约 110–145 行），修的却是仓库文档里写明了、而某个实现悄悄违反的契约。

为什么不从 issue 开始

抢 issue 的路径有三道关卡：要等一个合适的 issue、要和别人竞争、要猜维护者的心意。对第一次给陌生大仓库贡献的人来说，这三道关都在消耗热情。

我换了一条路：直接读代码，找「文档说了什么」和「实现做了什么」之间的裂缝。这类 bug 不需要领域判断，只需要耐心对照，而且维护者很难拒绝——因为它违背的是仓库自己写下的契约。

一条可复用的启发式

测试不对称就是 bug 定位器。

同一个接口往往有多个实现。如果只有其中一个实现为某个不变量写了回归测试，那么没被测到的那个「兄弟实现」，大概率就是 bug 所在。测试写在哪里，就说明作者当时在哪里踩过坑、在哪里没踩过。

反过来，这也是一个非常实用的阅读大型代码库的方法：先找测试，测试是作者留下的意图说明书；再找没被测试覆盖的平行实现，那里藏着不一致。

小 diff 也能被认真 review

很多人以为大贡献才值得提。实际上，小、精确、带回归测试的修复，是最容易被合并的那一类：review 成本低、风险可控、语义清晰。三个 PR 从提出到合并分别是约 12h、8h、4h。

给开源做贡献，难的不是写代码，是找到那个「值得修、修得动、修得对」的点。我把它固化成了一个 skill：oss-pr-skill，从仓库筛选、自挖 bug、红绿测试证明，到 CI 和 review 处理，全流程可复用。
