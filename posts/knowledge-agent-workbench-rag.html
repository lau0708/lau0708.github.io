手写 Workflow 还是 LangGraph：同一个 RAG 做两遍对照

Lau · 2026-10-31 · knowledge-agent-workbench 复盘

在 knowledge-agent-workbench 里，我把同一个 RAG + Agent 工作流做了两遍：一遍手写 Workflow，一遍用 LangGraph。不是为了炫技，而是想搞清楚框架到底帮我做了什么、没做什么。

双存储索引 + 混合检索

检索层用 SQLite 存结构化元数据、ChromaDB 存向量，走混合检索——关键词命中负责精确，向量召回负责语义。bge-small-zh 做嵌入，模型端接 DeepSeek，整体是本地优先、可自部署的形态。

手写一遍，才知道每个节点在干什么

手写 Workflow 没有任何魔法：状态就是一个显式的 dict，节点就是函数，边就是 if/else。它的好处是完全可控、好调试——任何一个环节的行为，代码里看得一清二楚。坏处是样板代码多，状态一复杂，维护成本就上来。

再用 LangGraph 对照一遍

LangGraph 把状态管理、节点/边、检查点这些通用能力做成了基础设施。同一套流程，用图来表达更清晰，也自带可观测性。但代价是：你得先理解它的状态模型和执行语义，否则出问题时会觉得它在黑盒里。

对照的意义

做完两遍，最大的收获是面试和实际排障时，能讲清楚「框架替我们解决了什么、我们仍然要对什么负责」。配套的 HITL 审批和 Trace 监控，也建立在对流程有完整理解的基础上，而不是把框架当黑盒调参数。
