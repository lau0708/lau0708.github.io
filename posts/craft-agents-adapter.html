跨境电商 Agent 平台——把 N 个后台收敛成一套工具调用

Lau · 2026-10-26 · 工作复盘 · 风越科技 Craft Agents 平台

跨境电商的经营决策，第一步就卡在数据上：库存、广告、订单、客服工单，分散在多个后台系统里，口径不一致、时点不一致。Agent 要在这些系统之间自主完成「发现异常 → 定位根因 → 决策 → 执行」，如果每一步都按各后台自己的接口去写，主流程会被耦合成一团乱麻。

统一数据接入：把异构后台收敛成一套标准工具调用，Agent 主流程不感知差异

一、问题不在接口多，在于没有统一的工具契约

异构后台有两种典型形态：已经 MCP 化的，和只有 HTTP API 的。它们的分页方式、鉴权方式、错误码、时间口径都不一样。Agent 主流程一旦直接感知这些差异，每接一个系统就要改一次主流程，平台就退化成了「一个后台写一套流程」。

二、Adapter 收敛，主流程面向标准契约

做法是：基于 ServerBuilder 统一接入框架，设计统一数据源 Adapter，把 MCP 与 HTTP API 收敛成同一套标准工具调用。对外暴露统一的参数结构、返回结构和错误语义，对内再翻译成各后台自己的协议。

  • 新数据源接入不改 Agent 主流程——主流程只面向标准工具契约，差异被 Adapter 隔离；
  • 口径与时点统一在 Adapter 层处理，而不是散落在每个调用点；
  • 错误码归一，Agent 看到的是同一种失败语义，而不是某家后台的原始报错。

三、为什么这一步值得先做

Agent 的推理质量上限，取决于它拿到的事实质量。数据接入层不统一，后面再好的诊断、决策，都建立在不一致的数据上——「发现异常」的第一步就错了，后面的闭环再完整也白搭。这也是为什么在做权限、评测之前，先把数据入口做干净。

四、复盘

工程上最有价值的一层抽象，往往不在模型附近，而在最脏的数据边界。Adapter 做的不是「把接口接上」，而是把「口径」和「时点」这两件最影响判断的事，在源头统一掉。
