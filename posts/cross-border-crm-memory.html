cross-border-crm 复盘——让 Agent 在受控边界下读写真实客户数据

Lau · 2026-11-14 · github.com/lau0708/cross-border-crm

仓库：lau0708/cross-border-crm · Next.js / React / TypeScript · Supabase · Pi Agent Core

一句话：CRM 保存业务事实，Agent 驱动跟进行动，Harness 管理执行边界与授权。

一、背景：两个「会伤人」的问题

跨境销售在 WhatsApp 上跟进客户，有两个根问题：记忆不可信——谁说过什么、客户偏好哪些，散落在会话里，Agent 分不清事实与猜测；自动跟进危险——没有约束的自动发送可能把「在谈」写成「已成交」，造成真实损失。

所以这个项目的命题不是「做一个 Agent 聊天机器人」，而是如何让 Agent 可信地读写真实 CRM 数据。

二、记忆：排序器可以做，事实源不行

一个常见设计错误，是把向量记忆（Mem0）当成客户事实的唯一来源。它天然有召回偏差、幻觉和过期信息——把「没检索到」误判成「客户没有这个偏好」，就会在跟进时犯事实错误。

这里的边界划得很清楚：

  • 本地 SQL 是唯一权威，保存人工确认过的客户事实；
  • Mem0 只做排序，对已确认条目排序，绝不做事实源；
  • 远端命中须过归属标识、运行标识、内容哈希三重核对，并映射回本地记录 ID，否则丢弃；
  • 服务不可用时回退本地读取，并标明覆盖范围——绝不把「没读到」包装成「没有」。

一句话：能查证的事实才进系统，模型只负责在这些事实之上排序和表达。

三、授权：只读的专家，单一的写者，分级动作

四个内置 Agent 各司其职：CRM 情报员汇总证据做客户画像，销售运营 Agent 排查停滞商机、更新字段，客户沟通 Agent 起草回复并核对承诺依据，CRM 主管 Agent 跨漏斗调查异常并组织协作。

但关键约束是：专家只做只读证据生产者，父流程是唯一写者。受控执行 Harness 把动作按风险分类：

  • 读取与可补偿写入——自动执行；
  • 外部动作——经人工确认；
  • 不可逆动作——最严格的门控。

同时支持暂停、恢复、取消、租约、重试与累计预算控制。专家以「字段值哈希 + 来源版本」产出断言，父流程据此区分事实分歧、版本漂移与互补片段。

四、跟进与 Mission 续跑：方向变了，旧动作要作废

负责人调整商机跟进方向时，以 Mission 方向版本开新 Run，撤销旧待执行动作、作废旧草稿、暂停旧客户发送；成功回合里核对新方向是否真的进入最终模型上下文，并把接收确认与运行消息同事务落库。方向版本与接收记录可对应追溯，新指令照样要再过一次独立授权。

五、评测：两层检查拦截「报告撒谎」

即使每条引用都指向真实记录，结论仍可能写错——比如把「在谈」写成「已成交」。所以评测分两层：先核对成功工具观察里的来源标识与结构化字段，再跑独立语义 Judge，取更严格的一层合并结论，并区分「引用未观察」「字段矛盾」「语义待复核」三类问题。

已存评价必须匹配运行材料、评测规范、模型版本——资料变化后不能沿用旧高分，否则评测本身也在漂移。Trace 经 Langfuse 投递，失败样本进回归集。

六、诚实的验收

2026-10-05 工程复核：类型检查、lint、构建与全量单测通过，单测 1,324 个文件、12,958 项。但项目状态写得很克制：当前为内部研发版本，真实运行记录已做脱敏回放，业务结果由证据与验收条件核验——没有把「跑通」包装成「生产可用」。

七、复盘

Agent 原生 CRM 最难的不是让模型会聊天，而是让「写」这个动作可交代：事实有唯一权威，写有单一入口，外发有过闸门，结论有评测。把这几条做成不变量，Agent 才谈得上「可信」，而不是「看起来聪明」。
