把开源贡献做成可复用的流程——oss-pr-skill 的四个阶段

Lau · 2026-11-08 · oss-pr-skill

给 deer-flow 提的 3 个 PR 合并之后，我把整条路径固化成了一个 skill：oss-pr-skill。目标只有一个：让下一次贡献不再从零开始，并且每一步都可交代。

阶段一：仓库筛选

不是所有仓库都值得投入。先判断三件事：维护者活不活跃、合并通道顺不顺、规则清不清楚。一个没人 review 的仓库，PR 提了也是石沉大海。先看合并历史与 CONTRIBUTING，再决定投不投入。

阶段二：自挖不变量 bug

不抢 issue、不先问维护者。直接读代码，找「文档说了什么」和「实现做了什么」之间的裂缝。这类 bug 违背的是仓库自己写下的契约，维护者很难拒绝，而且不需要领域判断。

阶段三：红绿测试证明

先写一条会失败的回归测试复现 bug（红），再做最小修复让它通过（绿）。红绿证明让 reviewer 一眼看到问题边界和修复范围，也证明你不是碰运气改对的。

阶段四：CI 与 review

盯 CI、认真回应 review。小 diff、带测试、语义清晰，是合并最快的那一类。最后把「问题、决策、动作、结果」沉淀成一条面试叙事——开源贡献真正的价值，一半在 PR 本身，一半在你能否讲清楚它是怎么来的。

为什么做成 skill

一次性贡献靠运气，可复用的贡献靠流程。把「找 bug 的启发式」「红绿证明」「review 沟通」固化下来，意味着下一次贡献的时间成本大幅下降，也意味着面试时我能拿出一个可演示的方法论，而不是一个孤立的 PR。
